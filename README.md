# 🗄️ Database Structure

The database is named:

```text
HotelSalesDB
```

It contains five primary tables:

```text
Customers
Rooms
Staff
Bookings
Payments
```

### Relationship Overview

```text
Customers
    │
    │ 1-to-many
    ▼
Bookings ───────────► Rooms
    │
    │
    └───────────────► Staff
    │
    │ 1-to-many
    ▼
Payments
```

The `Bookings` table acts as the central transactional table connecting customers, rooms, staff, and payments.

# 👤 Customer Analysis

Customer behavior is analyzed using booking history.

The analysis identifies:

- Customers with multiple bookings.
- Highest-spending customers.
- Customer booking frequency.
- Customer-wise total spending.
- Customers whose spending is above average.

Example:

```sql
SELECT
    c.CustomerID,
    CONCAT_WS(' ', c.FirstName, c.LastName) AS CustomerName,
    SUM(b.TotalAmount) AS TotalSpent
FROM Customers c
JOIN Bookings b
    ON c.CustomerID = b.CustomerID
GROUP BY c.CustomerID, c.FirstName, c.LastName
ORDER BY TotalSpent DESC;
```

# 🧠 Subquery Analysis

Subqueries are used to answer more advanced questions.

Examples include:

- Bookings above average booking value.
- Rooms priced above average room price.
- Customers spending above average customer spending.

Example:

```sql
SELECT
    BookingID,
    CustomerID,
    TotalAmount
FROM Bookings
WHERE TotalAmount > (
    SELECT AVG(TotalAmount)
    FROM Bookings
);
```

# ⚙️ SQL Trigger

The project demonstrates a database Trigger:

```text
trg_delete_booking_payment
```

The Trigger automatically deletes related payment records when a booking is deleted.

Conceptually:

```text
Delete Booking
      ↓
Trigger Executes
      ↓
Delete Related Payment
```

This demonstrates automated database operations and helps maintain consistency between related transactional records.

> **Note:** In a production database, cascading foreign keys (`ON DELETE CASCADE`) would often be considered instead of a manual trigger for this type of referential cleanup.
